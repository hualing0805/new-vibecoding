# 论坛内容模块

## 职责

论坛内容模块是产品主干，负责板块、帖子、回复和标签。它决定论坛是否像论坛，而不是像一个 AI 聊天壳。

第一阶段功能：

- 板块列表。
- 帖子列表、详情、发布。
- 回复列表、发布。
- 标签展示与提交。

## 设计思路

帖子和回复都保留状态字段，而不是直接物理删除。论坛天然需要治理、恢复、审计和用户争议处理；状态比删除更适合承载这些流程。

帖子列表只返回摘要，不返回完整正文。详情页再加载正文和回复。这样首页扫描更快，也避免 AI 摘要、回复列表等重内容拖慢列表。

## 功能设计

### 板块列表

返回板块名称、slug、描述和主题数。

设计理念：板块是论坛的信息路标，首页和发帖页都要用它。第一阶段不做复杂层级，但保留 `parent_id` 和排序字段，后面可以扩为多层板块。

### 帖子列表

支持按板块、关键词和排序方式查询。

设计理念：列表页优先服务扫描，字段包括标题、摘要、作者、标签、回复数、点赞数、收藏数、浏览数和创建时间。正文、回复、治理记录不出现在列表接口里。

### 帖子详情

返回完整正文、作者、标签、互动统计和 AI 摘要缓存。

设计理念：详情页是阅读和讨论场景，可以承载更完整的上下文。AI 摘要放在详情响应里，是为了让前端不用再猜摘要缓存来自哪里。

### 发布帖子

输入板块、标题、正文和标签名。

设计理念：后端接收标签名而不是标签 ID，方便发帖编辑器接入 AI 标签推荐。正式落库时由后端负责查找或创建标签，避免前端维护标签字典。

### 回复帖子

第一阶段只做一级回复。

设计理念：一级回复足够支撑 MVP 讨论体验。楼中楼会显著增加通知、排序、折叠和治理复杂度，等主流程稳定后再加。

## 后续实现要点

- 发布和回复都要记录作者 ID。
- Markdown 渲染前要做 XSS 清理。
- 帖子列表需要分页。
- `reply_count`、`like_count`、`favorite_count` 可先同步更新，后续高并发再异步聚合。
- 全文检索先用 MySQL FULLTEXT，后续再接搜索服务。
