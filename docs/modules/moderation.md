# 治理模块

## 职责

治理模块负责举报、处理和审计。AI 可以给风险提示，但不能替代版主或管理员做最终决定。

第一阶段功能：

- 用户举报帖子或回复。
- 管理员查看举报队列。
- 管理员处理举报。
- 写入处理记录。
- 管理台治理标签支持状态筛选和详情侧栏。

## 设计思路

举报和处理分开建模。举报是用户提交的线索，处理记录是管理动作的事实。一个举报可以被驳回，也可以触发隐藏、锁定或警告。

AI 风险字段只作为提示，不作为最终状态。这样可以避免模型误判直接影响用户内容。

## 功能设计

### 提交举报

输入目标类型、目标 ID、原因和补充说明。

设计理念：目标类型加目标 ID 的组合能覆盖帖子、回复，后续还能扩展到用户资料、私信等资源。

### 举报队列

管理员查看待处理举报列表。M7 起前端管理台支持全部、待处理、已处理、已驳回筛选。

设计理念：治理场景最需要“快速扫描”。列表字段包括目标、原因、AI 风险、状态、时间，点进详情后再看原文和上下文。

### 处理举报

输入动作和备注，动作可以是通过、驳回、隐藏、锁定、警告。

设计理念：处理接口只接受明确动作，不接受自然语言指令。管理员可以参考 AI 建议，但系统落库的是人工选择。

### 审计记录

每次处理写入 operator、目标、动作、备注和 traceId。

设计理念：治理行为必须可复盘。后续出现用户申诉时，不能只看到内容状态，还要看到谁在什么时候基于什么理由做了处理。

## 后续实现要点

- 版主只能处理自己板块内的内容。
- 管理员可以处理全站内容。
- AI moderation check 可以在发帖前调用，也可以在举报队列里调用。
- 审计记录不能被普通删除。
- 治理台后续可以增加按板块、风险等级和处理人筛选。
