# 互动与通知模块

## 职责

互动模块负责用户对内容的轻量反馈，通知模块负责把“和我有关的变化”送回用户。

第一阶段功能：

- 点赞帖子。
- 取消点赞帖子。
- 查询帖子互动状态。
- 点赞回复。
- 取消点赞回复。
- 查询回复互动状态。
- 收藏帖子。
- 取消收藏帖子。
- 查询当前用户收藏主题。
- 通知列表。
- 未读通知数量。
- 标记通知已读。

## 设计思路

点赞和收藏是独立动作，不能混在帖子更新接口里。这样可以清楚表达用户意图，也方便做幂等处理。

通知不在每个业务接口里直接展开复杂逻辑。业务服务只写入结构化通知，通知列表负责展示。后续加 WebSocket 时，可以复用同一份通知数据。

## 功能设计

### 点赞

同一用户对同一目标同一类型只能点赞一次。

设计理念：点赞是状态，不是计数按钮。接口应支持重复请求的幂等处理，避免用户连点导致统计错误。M3 中点赞接口返回当前状态和最新计数，详情页直接用后端结果刷新。

### 收藏

收藏只针对帖子，不针对回复。

设计理念：收藏的主要用途是形成用户个人知识库，帖子比单条回复更稳定。M3 中新增当前用户收藏列表，前端复用主题列表展示收藏内容。回复收藏可以作为后续扩展。

### 通知列表

返回通知类型、标题、正文、是否已读、创建时间。

设计理念：通知 payload 以后可以保存跳转目标、操作者、目标类型等结构，但列表展示要先稳定，不让前端直接依赖复杂 JSON。M3 中新增未读数量接口，顶部通知入口可以轻量显示状态。

### 标记已读

单条通知标记为已读。

设计理念：第一阶段先做最小动作。批量已读和未读数可以在通知中心稳定后补。

## 后续实现要点

- `reactions` 表要有唯一索引防重复。
- `favorites` 表要有唯一索引防重复。
- 取消动作找不到记录时可以视为成功，提升幂等性。
- 通知 payload 用 JSON 保存扩展信息，但展示字段需要独立 DTO。
- 用户回复或点赞自己的内容时不通知自己。
- 重复点赞不重复写通知，取消点赞不删除历史通知。
- 后续可以增加批量已读、通知跳转目标和 WebSocket 推送。
