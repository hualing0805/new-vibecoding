# ThreadMind 开发标准

本标准用于约束 ThreadMind 后续每一次开发。任何功能开发、修复、重构、文档补充或联调收口，都必须按这里的流程执行，确保项目状态、开发计划、阶段手册、验证结果和 GitHub 提交都可追溯。

## 1. 总原则

- 每次开发都要先确认当前目标，不在目标外做无关重构。
- 每次开发都要有计划，开发结束要有手册，最终要提交并推送到 GitHub。
- 重要约定写进仓库文档，不只留在聊天记录里。
- 所有提交信息和最终说明默认使用中文。
- 不提交临时文件、密钥、空文件、日志文件、构建产物或本地机器私有配置。
- 工作区已有但与本轮无关的改动不得随意回滚；如会影响本轮开发，先说明再处理。

## 2. 开发前流程

每次开发开始前必须完成：

1. 查看仓库状态。

```powershell
git status --short
git branch --show-current
git remote -v
```

2. 阅读相关文档和代码入口。

- 产品和范围：`PRODUCT.md`
- 开发标准：`docs/development-standard.md`
- 开发手册索引：`docs/development-manuals/README.md`
- API 契约：`docs/api-contracts.md`
- 相关模块文档：`docs/modules/`

3. 明确本轮开发计划。

计划至少包含：

- 本轮目标。
- 需要改哪些模块。
- 需要新增或更新哪份开发手册。
- 预计验证方式。
- 是否需要提交数据库迁移、环境变量或启动脚本。

4. 如果计划较大，先在对话里给出简短计划，再开始改文件。

## 3. 开发中流程

开发过程中必须遵守：

- 优先沿用现有项目结构和命名风格。
- 数据库变更先写迁移脚本，再写依赖该结构的业务代码。
- 前后端接口变更必须同步 `docs/api-contracts.md`。
- 模块边界变化必须同步 `docs/modules/` 或 ADR。
- 每个阶段的关键决策要写进开发手册。
- 不把 API Key、数据库密码、JWT 密钥、SSH 文件提交到仓库。
- 修改文件前后尽量保持改动范围清晰，不把无关格式化混入功能提交。

## 4. 开发手册标准

每次开发都必须新增或更新一份阶段手册，放在：

```text
docs/development-manuals/
```

文件名建议：

```text
阶段-主题.md
```

示例：

```text
M2.5-real-integration-and-tests.md
M3-interaction-notification.md
M4-agent-audit.md
```

手册必须包含：

- 阶段目标。
- 本阶段需要完成的事情。
- 已经如何完成。
- 本地使用或验收步骤。
- 本地验证命令和结果。
- 关键文件。
- 遗留风险和下一步建议。

如果本轮只是小修，也可以更新最近一份阶段手册，但必须在手册里写清楚本次补充内容。

## 5. 开发手册模板

```markdown
# 阶段名称开发手册

## 阶段目标

说明本阶段为什么做、做到什么程度算完成。

## 需要完成的事情

- 任务 1
- 任务 2
- 任务 3

## 已经如何完成

- 说明具体实现方式。
- 说明涉及的服务、页面、接口、数据库迁移或脚本。
- 说明关键取舍。

## 本地使用或验收步骤

写清楚从启动环境到验证功能的步骤。

## 本地验证

列出实际执行过的命令和结果。未执行的检查必须说明原因。

## 关键文件

- `path/to/file`

## 遗留风险

- 风险 1
- 风险 2

## 下一步建议

- 建议 1
- 建议 2
```

## 6. 验证标准

每次开发结束前，根据改动范围执行必要检查。

常规检查：

```powershell
git diff --check
```

Java 后端：

```powershell
cd backend-java
mvn test
```

如果系统没有 Maven：

```powershell
cd backend-java
..\.tools\apache-maven\bin\mvn.cmd test
```

Vue 前端：

```powershell
cd frontend-vue
npm.cmd run typecheck
npm.cmd run build
```

Python Agent：

```powershell
cd agent-python
python -m pytest
```

如果本机没有 Python，可使用 Codex 工作区运行时或说明未执行原因。

## 7. Git 提交和 GitHub 推送标准

每次开发结束后必须：

1. 确认工作区。

```powershell
git status --short
```

2. 只暂存本轮相关文件。

```powershell
git add <本轮相关文件>
```

不得暂存：

- `.env`
- 密钥、SSH 文件、证书
- 日志文件
- 临时空文件
- 本地 IDE 配置
- 非必要构建产物

3. 使用中文提交信息。

提交格式：

```text
动词 + 阶段/模块 + 简短结果
```

示例：

```powershell
git commit -m "完成M2.5真实联调与核心流程测试" -m "补充一键联调脚本、核心流程验收手册和数据库集成测试。"
```

4. 推送到 GitHub。

```powershell
git push origin <当前分支>
```

当前默认分支为 `main`。如果以后切到功能分支，推送当前分支并在最终说明中写清楚分支名。

## 8. 最终汇报标准

每次开发完成后，最终回复必须用中文简短说明：

- 本次做了什么。
- 关键文件在哪里。
- 执行了哪些验证，结果如何。
- 提交信息、提交哈希和推送分支。
- 如果有未完成或未验证内容，必须明确说明。

示例：

```text
已完成 M2.5 真实联调与核心流程测试。

本次补充了一键联调脚本、端到端验收手册和 Java 数据库集成测试。
验证：Java 测试通过，前端 build 通过，Python pytest 通过。
提交：abc1234 完成M2.5真实联调与核心流程测试，已推送到 origin/main。
```

## 9. 异常处理

- 如果测试失败，优先修复；不能修复时，不得假装通过，必须写明失败命令和原因。
- 如果网络、权限或本机环境导致无法验证，必须说明阻塞点。
- 如果 GitHub 推送失败，必须说明远程、分支、错误原因和下一步。
- 如果发现无关未提交改动，不要擅自回滚；提交时只包含本轮相关文件。
